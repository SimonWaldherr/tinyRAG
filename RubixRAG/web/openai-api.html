R3 als OpenAI-kompatibler RAG-/Werkzeug-Endpunkt

Diese Schnittstelle macht R3 für Programme nutzbar, die bereits die OpenAI-Chat-Completions-API sprechen: Open WebUI, IDE-Assistenten, interne Agenten oder eigene Automatisierungen. Sie verwenden eine normale OpenAI-Base-URL, erhalten aber Antworten, die je nach konfiguriertem Endpoint mit Ihrer R3-Wissensbasis angereichert sind und/oder R3s Werkzeuge nutzen können.

Warum das nützlich ist: R3 ist dabei nicht bloß ein Modell-Endpunkt. Je Endpoint lässt sich unabhängig wählen, ob R3s Wissensbasis-Suche (RAG) und/oder die konfigurierten Live-Werkzeuge (SQL, Shop, REST) mitwirken — bis hin zu einem reinen LLM-Zugang ganz ohne beides. Mit einem fest vorgegebenen Backend (z. B. azure) wird ein Endpoint zugleich zum kontrollierten Proxy für Azure OpenAI: Das aufrufende Tool braucht weder Azure-URL noch Azure-Schlüssel.

Mehrere Endpoints, ein Port

Ein gemeinsamer Port bedient beliebig viele benannte Endpoints — jeder mit eigenem URL-Pfad und eigener Fähigkeits-Kombination:

KombinationTypischer Einsatz
Nichts (RAG aus, Werkzeuge aus)Reiner LLM-Zugang — das Partner-Werkzeug bekommt genau das konfigurierte Standard-LLM, ohne R3-Wissen. Eigene System-Anweisungen des Aufrufers werden dabei unverändert durchgereicht.
Nur RAGGrounded Q&A ohne Werkzeugaufrufe — wie der Chat-Tab.
Nur WerkzeugeLive-Datenzugriff (SQL/Shop/REST) ohne Wissensbasis-Kontext.
RAG + WerkzeugeVolle Fähigkeit — wie ein Agent, nur über die OpenAI-Schnittstelle nutzbar.

Ein Endpoint ohne Namen wird unpräfigiert unter /v1/chat/completions bereitgestellt (praktisch, wenn nur ein Endpoint gebraucht wird); ein benannter Endpoint partner-a liegt unter /partner-a/v1/chat/completions.

Einrichtung

  1. Unter Einstellungen → API-Zugriff einen API-Key anlegen.
  2. Unter Einstellungen → OpenAI-kompatible API aktivieren, den gemeinsamen Port setzen, und mindestens einen Endpoint anlegen: Name (leer = Root-Pfad), RAG/Werkzeuge nach Bedarf, optional ein festes Backend und ein Zugriffs-Preset.
  3. Im anderen Tool als Base URL http(s)://R3-HOST:PORT[/ENDPOINT-NAME]/v1 und den R3-API-Key eintragen.

Verfügbare Modellnamen im model-Feld: local, azure, openai, openrouter, claude, gemini — sofern jeweils konfiguriert. Ist der Endpoint auf ein Backend fest eingestellt, wird das model-Feld des Aufrufers ignoriert. Ohne Modellangabe (und ohne feste Vorgabe) nutzt R3 das Standard-Chatprofil.

Schnelltest

curl http://R3-HOST:PORT/v1/chat/completions \
  -H "Authorization: Bearer R3_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"azure","messages":[{"role":"user","content":"Was wissen wir über Lieferzeiten?"}]}'

# Ein benannter Endpoint "partner-a":
curl http://R3-HOST:PORT/partner-a/v1/chat/completions \
  -H "Authorization: Bearer R3_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"messages":[{"role":"user","content":"Welche Artikel sind aktuell auf Lager?"}]}'

stream: true aktiviert Server-Sent Events. GET /v1/models (bzw. /ENDPOINT-NAME/v1/models) listet die für diesen Endpoint nutzbaren Profilnamen — bei fest vorgegebenem Backend nur dieses eine. Die API akzeptiert Textnachrichten und liefert eine Chat-Completions-kompatible Antwort; sie unterstützt absichtlich nur eine Antwort pro Request (n: 1).

Sicherheit

Jeder Aufruf benötigt einen R3-API-Key, für jeden Endpoint. Das Zugriffs-Preset eines Endpoints begrenzt serverseitig sichtbare Quelltypen und Werkzeuge; der aufrufende Client kann diese Begrenzung nicht lockern. Ein Endpoint ohne RAG/Werkzeuge zieht kein Preset heran. Verwenden Sie für die Datenbank zusätzlich immer einen Nur-Lese-Login.
