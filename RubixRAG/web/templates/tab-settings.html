Datenquellen (Connectors)

Import

Drosselung & Limits

Schützt sowohl R3 als auch die angebundenen Systeme davor, dass ein einziger Import in einem Rutsch riesige Mengen zieht (z. B. Zehntausende Tickets/Mails) oder die Gegenstelle mit Requests überflutet. Gilt für alle Connectoren. Resumierbare Quellen (IMAP, SharePoint-Delta) machen beim nächsten Lauf automatisch weiter, wo das Limit gegriffen hat — es geht nichts verloren, große Rückstände werden nur in Häppchen abgearbeitet.

SharePoint

Für den Import direkt aus einer oder mehreren SharePoint-Dokumentbibliotheken über Microsoft Graph. Braucht je Verbindung eine Azure-AD-App-Registrierung mit der application-Berechtigung Sites.Selected und Admin-Consent, plus eine explizite Freigabe für die jeweilige Site (macht die IT via Graph, nicht diese Einstellungsseite) — Client-Credentials-Flow, kein Anmeldedialog nötig. Nicht Sites.Read.All verwenden: das gibt tenant-weiten Lesezugriff (auch auf persönliche OneDrives und andere Geschäftsbereiche) statt nur auf die konfigurierte Site. Details siehe ANLEITUNG.md, Abschnitt „SharePoint".

Outlook / Exchange Online (Microsoft Graph)

Für ein oder mehrere gemeinsame/dienstliche Postfächer. Braucht je Verbindung eine application-Berechtigung Mail.Read (idealerweise per Exchange-Anwendungszugriffsrichtlinie auf das jeweilige Postfach beschränkt) und Admin-Consent. Kann dieselbe App-Registrierung wie SharePoint verwenden, wenn dort schon eine existiert.

OneDrive for Business

Importiert einen explizit ausgewählten OneDrive-/Microsoft-365-Drive über Microsoft Graph und hält ihn per Delta-Sync aktuell. Für jede Verbindung ist die unveränderliche Drive-ID erforderlich (nicht „Mein OneDrive“ oder eine E-Mail-Adresse); so bleibt der Umfang prüfbar. Die App benötigt eine passende application-Leseberechtigung für diesen Drive. Möglichst eine dedizierte, restriktiv berechtigte App verwenden – OneDrive-App-Rechte sind in vielen Tenants weiter gefasst als SharePoints Sites.Selected.

Microsoft Teams

Für einen oder mehrere Kanäle. Braucht je Verbindung eine application-Berechtigung ChannelMessage.Read.All und Admin-Consent — diese Berechtigung erlaubt tenant-weiten Lesezugriff auf Kanalnachrichten, daher den Zugriff auf diese App-Registrierung entsprechend beschränken. Anders als SharePoint/Outlook oben gibt es hier (noch) keine Struktur-Erkunden-Hilfe — Team-/Kanal-ID stattdessen von Hand aus der Teams-Web-URL des Kanals ablesen: „Kanal-Link kopieren" in Teams liefert eine URL der Form .../channel/19%3aKANAL-ID%40thread.tacv2/...?groupId=TEAM-ID&... — die Team-ID ist der groupId-Parameter (eine GUID), die Kanal-ID der Teil vor %40thread.tacv2 inklusive des vorangestellten 19%3a (in 19:…@thread.tacv2 URL-dekodiert).

IMAP (On-Prem Exchange / generische Postfächer)

Alternative zu Outlook/Exchange über Graph — funktioniert mit jedem IMAP-fähigen Postfach (On-Prem Exchange, Microsoft 365, …), braucht aber eigene Zugangsdaten statt einer Azure-AD-App. Mehrere Postfächer sind als getrennte Verbindungen möglich.

Konversationsbewusste Suchanfrage (Vorab-Umschreibung)

Zusätzlicher, optionaler Schritt vor jeder Chat-Antwort mit Gesprächsverlauf: ein eigener, schneller LLM-Aufruf formt aus einer Anschlussfrage wie „und bei Kistenpfennig?" eine eigenständige Suchanfrage (z. B. „Lieferantenrichtlinie Kistenpfennig"), nur für die Suche in der Wissensbasis — die Frage, wie sie im Chat angezeigt wird, und die Antwort des Hauptmodells bleiben unverändert. Ohne diesen Schritt sucht R3 bei einer Anschlussfrage nur mit deren eigenem (oft bedeutungsarmem) Text. Wird übersprungen, wenn noch kein Gesprächsverlauf vorliegt (erste Frage) — kostet sonst einen zusätzlichen LLM-Aufruf pro Anfrage, deshalb standardmäßig aus.

Confluence

Für einen oder mehrere Spaces. Nutzt einen Atlassian-API-Token (Atlassian-Konto → Sicherheit → API-Tokens) statt Passwort.

Jira

Für ein oder mehrere Projekte. Nutzt einen Atlassian-API-Token (Atlassian-Konto → Sicherheit → API-Tokens) statt Passwort — derselbe Token wie für Confluence funktioniert, falls der Account beides lesen darf.

Freshservice

Für eine oder mehrere Freshservice-Instanzen. Nutzt einen Freshservice-API-Key (Profil → API-Key) als HTTP-Basic-Benutzername statt Passwort.

GitHub

Importiert README, Issues und Pull Requests eines Repositories von GitHub.com oder GitHub Enterprise. Verwende einen feingranularen, nur lesenden Token, der auf genau dieses Repository beschränkt ist; der Token gehört bevorzugt in eine Umgebungsvariable. Code-Dateien und Wiki-Git-Repositories werden bewusst nicht blind gespiegelt – sie können als eigener Ordner-/Git-Export gezielt importiert werden.

SAP S/4HANA (OData)

Liest eine einzelne, ausdrücklich konfigurierte OData-Entity ausschließlich per GET. Lege ID-, Titel- und Inhaltsfelder fest; R3 setzt daraus einen $select-Filter und importiert keine anderen Felder. Unterstützt OData-V2- und V4-Antworten sowie Delta-Links, wenn der SAP-Service sie bereitstellt. Für interne Zertifikate die Unternehmens-CA im Betriebssystem/Container hinterlegen – Zertifikatsprüfung wird nicht abgeschaltet.

Server-Ordner (geplanter Import)

Für einen oder mehrere Server-Ordner, die R3 regelmäßig automatisch neu einliest (rekursiv) — der geplante Gegenpart zum einmaligen „Server-Ordner importieren" im Import-Tab. Unveränderte Dateien werden bei jedem Lauf übersprungen. Der Ordner muss für den R3-Serverprozess selbst erreichbar sein (lokaler Pfad oder bereits eingebundene Netzwerkfreigabe) — R3 bindet nichts selbst ein.

E-Mail (SMTP)

Wird bisher ausschließlich für die „Antwort an mich senden"-Funktion im Chat genutzt — R3 verschickt darüber immer nur an die eigene angemeldete AD-Mailadresse, nie an ein Freitextziel.

Werkzeuge (Live-Tools)

MSSQL (Live-Abfrage-Tool fürs Chat-Modell)

Kein Import — das Chat-Modell kann bei Bedarf selbst eine SELECT-Abfrage gegen diese Datenbank stellen (Function/Tool-Calling). Erfordert ein Chat-Modell mit Tool-Calling-Unterstützung; viele kleine lokale Modelle können das nicht, dann bleibt diese Einstellung wirkungslos. Der Datenbank-Login sollte nur Lesezugriff (SELECT) haben — die serverseitige SELECT-only-Prüfung ist zusätzlicher Schutz, kein Ersatz dafür.

SQL-Abfrage-Vorlagen (MCP-artige Konnektoren)

Am einfachsten und sichersten sind feste Vorlagen: „SQL-Vorlage hinzufügen“ erzeugt eine kleine, parameterisierte SELECT-Abfrage als Startpunkt. Ersetzen Sie nur Tabelle/Spalten und beschreiben Sie, wann das Modell sie nutzen soll. Werte gehören immer in {parameter}, nie per Text-Einbau ins SQL. Freie SELECTs bleiben bewusst standardmäßig aus. Kommentare und Textwerte dürfen Schlüsselwörter enthalten; seiteneffektbehaftete SQL-Server-Befehle sowie SELECT … INTO werden abgewiesen.

Als JSON bearbeiten (Fortgeschritten)

Wird zusammen mit den übrigen Einstellungen über den Button "Einstellungen speichern" unten gespeichert — kein eigener Speichern-Button, wie bei den anderen Feldern auf dieser Seite.

Shop-Anbindung (de.rubix.com)

Kein Import — das Chat-/Agent-/Mail-Modell kann bei Bedarf selbst den Rubix-Onlineshop ansprechen (Function/Tool-Calling), live zum Zeitpunkt der Antwort, über drei getrennte Werkzeuge: Volltextsuche (Name, Artikelnummer, Hersteller, EAN, technische Kerndaten — bewusst ohne Preis/Lagerbestand), Auflösen einer bereits bekannten Produkt-ID (z. B. aus einer alten Bestellung/URL) zu Name und Artikelnummer, sowie aktuelle Verfügbarkeit/Lieferzeit/Preis zu bereits bekannten Artikeln. Preis/Lagerbestand werden bewusst nicht bei jeder Suche pauschal mitgeladen, sondern nur gezielt abgerufen, wenn tatsächlich danach gefragt wird. Alle drei Werkzeuge benötigen ein echtes, hier hinterlegtes Shop-Konto.

Generische REST-Connectoren

Ein wiederverwendbarer Zugang zu einem beliebigen REST-System (z. B. dem SAP-se16-Gateway https://logistic.rubix-intern.de, einem internen Microservice oder einer Drittanbieter-API), auf den sich die HTTP-Abfrage-Vorlagen unten per auth_source (dem Namen) beziehen. Der Connector legt fest, wohin eine Vorlage überhaupt aufrufen darf (die Basis-URL pinnt den erlaubten Host — SSRF-Schutz) und wie authentifiziert wird (keine / Basic / Bearer / Header-API-Key), plus optionale statische Header. Zugangsdaten möglichst über eine Umgebungsvariable hinterlegen statt direkt. Selbst kein Import — nur ein Live-Zugang für die Vorlagen unten.

Wird zusammen mit den übrigen Einstellungen über "Einstellungen speichern" unten gespeichert. Ein REST-Connector wird erst nutzbar, sobald ihn eine aktivierte HTTP-Abfrage-Vorlage unten über auth_source referenziert.

HTTP-Abfrage-Vorlagen (generische Live-Konnektoren)

Die REST-Entsprechung der SQL-Abfrage-Vorlagen oben: statt für jede weitere Live-Abfrage (Freshservice-Ticket-Status, Jira-Issue-Status, Confluence-Live-Suche, …) einen eigenen Code-Baustein zu schreiben, wird hier nur noch eine URL-Vorlage mit {platzhalter}-Parametern konfiguriert — die Zugangsdaten kommen von einer der eingebauten Quellen (confluence/jira/freshservice/none) oder von einem oben definierten generischen REST-Connector (per Name als auth_source) — so lassen sich z. B. SAP-se16-Endpunkte wie https://logistic.rubix-intern.de/se16/ZITEC/mara/{matnr} live anbinden. Jeder deklarierte Parameter muss in url_template als {name} vorkommen; die URL muss https nutzen und (außer bei auth_source: "none") denselben Host haben wie die Basis-URL des referenzierten Konnektors — wird beim Speichern geprüft, eine ungültige Vorlage wird komplett abgelehnt. response_json_path ist optional (z. B. "tickets") und kürzt die Antwort auf nur dieses Feld. Wie oben gilt: Beschreibung, Parameter-Beschreibung/-Beispiel und Rückgabe-Hinweis sieht das Modell wortwörtlich.

Als JSON bearbeiten (Fortgeschritten)

Wird zusammen mit den übrigen Einstellungen über den Button "Einstellungen speichern" unten gespeichert — kein eigener Speichern-Button, wie bei den SQL-Abfrage-Vorlagen oben. Jede aktivierte Vorlage wird als eigenes Werkzeug angeboten, gesteuert über die Werkzeug-Kategorie http in den Zugriffs-Presets unten.

Werkzeug-Routing (Vorab-Entscheidung)

Zusätzlicher, optionaler Schritt vor jeder Chat-/Agent-/Mail-Antwort: ein eigener, schneller LLM-Aufruf entscheidet nur, ob eines der oben konfigurierten Live-Werkzeuge (MSSQL, Shop, HTTP-Vorlagen) gebraucht wird, führt es bei Bedarf sofort aus, und gibt das Ergebnis zusammen mit dem Wissensbasis-Kontext an die eigentliche Antwort weiter. Ergänzt die eigenständige Werkzeug-Entscheidung des Hauptmodells selbst, ersetzt sie nicht — wählt die Vorprüfung das falsche oder gar kein Werkzeug, kann das Hauptmodell in seiner eigenen Runde trotzdem noch selbst eines aufrufen. Kostet einen zusätzlichen LLM-Aufruf pro Anfrage — deshalb standardmäßig aus. In der Arbeitsschritte-Anzeige erscheint dieser Schritt als eigener, gekennzeichneter Eintrag ("Vorprüfung: …").

Agent

Die Agent-Stufe im Chat darf — anders als Instant/Standard — Werkzeuge mehrfach und iterativ einsetzen (Wissensbasis-Suche, Quellen-Volltext, Quellenliste; bei aktivierten Antwortentwürfen zusätzlich Mail-Entwürfe, für Admins inkl. Ablage im Postfach-Entwürfe-Ordner; bei aktiviertem MSSQL auch die SQL-Werkzeuge). Jede Werkzeug-Ausführung wird protokolliert (unten).

Letzte Agent-Werkzeug-Aufrufe

        Zugriff & Sicherheit

        Zugriffs-Presets (Einsatzzweck)

        Eine zweite, von der Abteilungs-Zugriffskontrolle oben unabhängige Einschränkungs-Achse: nicht WER fragt, sondern WOFÜR — z. B. ein Preset "Kundenkommunikation", das nur Shop und Wissensbasis-Dateien erlaubt, aber keine internen PST-Postfächer. Ein Preset kann nie mehr zeigen, als die Abteilungs-Zugriffskontrolle ohnehin erlaubt — beide gelten gemeinsam als Schnittmenge. Im Chat wählt die fragende Person selbst ein Preset (Dropdown); Agent und Antwortentwürfe nutzen je ein fest hinterlegtes Preset (siehe die Felder in den jeweiligen Karten oben). Leere kinds/tools bzw. ein nicht existierendes/leeres Preset bedeuten „keine Einschränkung auf dieser Achse“. JSON-Array aus Objekten {"name", "display_name", "kinds": [...], "tools": [...]} — name ist die stabile ID (wird in den obigen Preset-Feldern und im Chat-Dropdown referenziert), kinds sind erlaubte source_kind-Werte (z. B. file, pst_email, shop), tools erlaubte Werkzeug-Kategorien (mssql, shop, http, sharepoint_search, web_search, azure_bing_search).

        Wird zusammen mit den übrigen Einstellungen über den Button "Einstellungen speichern" unten gespeichert — kein eigener Speichern-Button, wie bei den SQL-Abfrage-Vorlagen oben.

        Zitate (URL-Zuordnungen)

        Ordnet Pfad-Präfixe Web-URLs zu, damit Citation-Chips direkt auf das Original verweisen (SharePoint, Intranet, Dateiserver). Eine Zuordnung pro Zeile im Format Pfad-Präfix → URL-Präfix.

        Zitate (Sichtbarkeit je Quelltyp)

        Legt je Quelltyp (source_kind) fest, ob dessen Treffer als anklickbare Quelle/Zitat in der Antwort angezeigt werden. Ein nicht aufgeführter Typ bleibt sichtbar (Standardverhalten). Auf false gesetzte Typen werden weiterhin zur Beantwortung herangezogen — nur die Quellenangabe selbst wird unterdrückt, z. B. für PST-Postfachimporte aus Datenschutzgründen. Ein Eintrag pro Zeile im Format source_kind = true/false.

        Bekannte Quelltypen: file, pst_email, pst_attachment, imap_email, imap_attachment, outlook_email, outlook_attachment, sharepoint_file, sharepoint_page, sharepoint_link, onedrive_file, confluence_page, jira_issue, teams_message, web_page, freshservice_ticket, github_readme, github_issue, github_pull_request, sap_s4_record.

        Zugriffskontrolle je Quelltyp (Abteilungen)

        Schränkt einen Quelltyp (source_kind) auf bestimmte Abteilungen ein — anders als die Sichtbarkeits-Einstellung oben verhindert das, dass die Inhalte überhaupt in eine Antwort einfließen (echte Zugriffskontrolle, nicht nur Zitat-Anzeige). Ein nicht aufgeführter Typ bleibt für alle durchsuchbar, auch für nicht angemeldete Besucher:innen. Die Abteilung wird beim LDAP-Login automatisch aus den AD-Attributen department/title klassifiziert (siehe department.go) — ohne LDAP-Login (siehe unten) hat diese Einstellung keine Wirkung für angemeldete Nutzer:innen, da niemand sich anmelden kann. Ein Eintrag pro Zeile im Format source_kind = Abteilung1,Abteilung2.

        Bekannte Quelltypen: siehe Abschnitt „Zitate (Sichtbarkeit je Quelltyp)“ oben (inkl. freshservice_ticket). Bekannte Abteilungs-Codes: GF, Zoll, FiBu, IT, QM, SAP, Team Prozesse, EBusiness, Einkauf, PDM, Marketing, Personal, Controlling, Empfang, Vertrieb, Logistik, Spezial, Fertigung, Fahrdienst, default (default = angemeldet, aber Abteilung/Titel konnte keiner Regel zugeordnet werden). Diese Liste zeigt nur die eingebauten Standard-Regeln — falls unter Prompts → „Abteilungs-Regeln“ eine eigene department_rules.json aktiv ist, können die tatsächlich vergebenen Codes davon abweichen; dort nachsehen, bevor hier Codes eingetragen werden.

        LDAP / Active Directory

        Ersetzt das geteilte Admin-Passwort durch echte AD-Anmeldedaten (Benutzername + Passwort) mit echter serverseitiger Sitzungsprüfung — nicht nur eine UI-Anzeige wie beim bisherigen Passwort-Gate. Ohne Aktivierung ändert sich nichts am bisherigen Verhalten. Anmeldung ist jetzt für alle Mitarbeitenden gedacht, nicht nur für Admins: jeder erfolgreiche AD-Login erhält eine normale Sitzung (für Abteilungs-Zugriff/Personalisierung oben), unabhängig davon, ob die Gruppenbedingung unten erfüllt ist — die Gruppe entscheidet ausschließlich über Admin-Zugriff. R3 liest dabei nur Anzeigename, Konto-/UPN, Mail, Abteilung, Titel, Standort, Unternehmen, Gruppen und eine interne stabile Directory-ID; Personalnummern, Telefon, Manager und Anschrift werden weder abgefragt noch gespeichert.

        Solange weder die Gruppe noch diese Liste gesetzt sind, erhält jeder erfolgreich authentifizierte AD-Account Admin-Zugriff (wird im Server-Log als Warnung vermerkt). Sobald eine der beiden gesetzt ist, erhalten Accounts, die weder in der Gruppe noch in der Liste sind, trotzdem eine normale (nicht-admin) Sitzung.

        LDAP selbst hat keine eigenen Dienstkonto-Zugangsdaten zum Testen — der Test unten führt daher einen echten Bind-Versuch mit einem beliebigen AD-Testkonto durch, genau wie ein normaler Login.

        Lokale Anmeldung (Benutzerkonten)

        Individuell angelegte lokale Konten mit eigenem Passwort (bcrypt-gehasht) — eine Alternative und Ergänzung zur AD/LDAP-Anmeldung oben, z. B. für externe Partner oder Testkonten ohne AD-Konto. Die Konten selbst werden im Tab „Benutzer" verwaltet und im konfigurierten Speicher-Backend abgelegt (tinySQL oder SQLite, siehe „Speicher-Backend"), nicht in dieser Einstellungsdatei. Sobald lokale Anmeldung ODER LDAP aktiv ist, sind die Admin-Bereiche serverseitig wirklich geschützt (nicht mehr nur UI-versteckt).

Interaktive Dokumentation mit Schema-Ansicht und „Ausprobieren"-Funktion: /api/docs (maschinenlesbar unter /api/openapi.json, OpenAPI/Swagger-Format). Dieselben Keys unten funktionieren auch für die OpenAI-kompatible API weiter unten.

        OpenAI-kompatible API (für andere Tools)

        Stellt R3 auf einem eigenen, gemeinsamen Port als einen oder mehrere OpenAI-kompatible Chat-Completions-Server bereit — jeder unten definierte Endpoint bekommt seinen eigenen URL-Pfad (/<name>/v1/chat/completions, leerer Name = unpräfigiert /v1/chat/completions) und entscheidet unabhängig, welche R3-Fähigkeiten er nutzt: nur das konfigurierte Standard-LLM (z. B. Azure, ganz ohne Wissensbasis/Werkzeuge), zusätzlich die Wissensbasis-Suche (RAG), zusätzlich Werkzeuge (Shop, MSSQL, HTTP-Vorlagen) — oder beides zusammen. So kann ein Partner-Werkzeug genau die Fähigkeiten bekommen, die es braucht, ein anderes einen reinen LLM-Zugang — z. B. Chat-Oberflächen wie Open WebUI, KI-Erweiterungen in Programmier-Editoren, oder andere Programme, die eigentlich für ChatGPT/OpenAI gebaut wurden: die lassen sich damit stattdessen auf R3 umleiten, ohne eigene Anpassung an dem Partner-Werkzeug. Einrichtung, Beispiele und Hintergrund öffnen. Erfordert immer einen gültigen API-Key (siehe oben) für jeden Endpoint — anders als bei /api/ask gibt es hier keine Option, die Schlüsselpflicht abzuschalten. Änderungen wirken sofort nach „Einstellungen speichern" (der Server wird bei Bedarf neu aufgesetzt), ohne Prozess-Neustart.
